# Use Cases & Decision Points

## 0. System context (2–4 sentences)
- System name: CityTransit Control.
- Target users: пасажири, диспетчери, водії, депо, аналітики.
- Main value: актуальне ETA та контроль інтервалу руху на підставі перевірених даних.
- AI component role (1 sentence): C4 прогнозує ETA, а правила C5 та диспетчер контролюють використання результату.

Виконав: Ковач Роман Романович, Б2F201ДОН23. Продовження ПР1–2; C1–C7 та D1–D3 відповідають ПР4. DP-01–03 зберігають зміст точок ПР4. Пороги є навчальними проєктними припущеннями, а не регламентом перевізника.

## A. Use Cases

### UC-01: Отримати актуальний час прибуття
- Primary actor: Пасажир
- Secondary actors: Диспетчер; сервіс розкладів
- Trigger: Вибір зупинки та маршруту
- Preconditions: Зупинка існує у D1; доступний розклад
- Main flow:
  1) C1 передає route_id і stop_id до C5.
  2) C3 знаходить найближчий рейс і формує часовий зріз.
  3) C2/C3 перевіряють вік та повноту телеметрії [DP-05].
  4) C4 прогнозує ETA та інтервал невизначеності.
  5) C5 обирає спосіб публікації прогнозу [DP-01].
  6) C1 показує ETA, інтервал та час оновлення; C7 фіксує режим.
- Alternative / exception flows: A1: сумнівний контекст → показати попередження, поставити випадок у чергу диспетчера. E1: немає моделі/даних → позначений розклад без удаваного live ETA.
- Output / outcome: Картка прибуття із часом актуальності та режимом forecast/schedule.
- Constraints (NFR): Ціль p95 відповіді ≤2 с; не показувати старі дані як актуальні.

### UC-02: Відновити інтервал між машинами
- Primary actor: Диспетчер
- Secondary actors: Водій; C6; служба руху
- Trigger: Сигнал про злипання машин
- Preconditions: Є два рейси одного маршруту та актуальний зріз
- Main flow:
  1) C3 зіставляє фактичний і плановий інтервали.
  2) C5 визначає, чи потрібна тривога [DP-04].
  3) Диспетчер відкриває картку з інтервалом, завантаженістю й поясненням.
  4) C5 перевіряє межі допустимої затримки; диспетчер обирає дію [DP-02].
  5) C6 доставляє лише підтверджене розпорядження.
  6) C7 зберігає автора, причину, квитанцію та подальший інтервал [DP-10].
- Alternative / exception flows: A1: диспетчер відхиляє затримку з причиною. E1: немає квитанції → резервний канал зв’язку, без повторної автоматичної команди.
- Output / outcome: Підтверджене розпорядження або обґрунтоване відхилення.
- Constraints (NFR): Жодної команди водію без людини; ідемпотентний decision_id.

### UC-03: Погодити додатковий випуск
- Primary actor: Диспетчер
- Secondary actors: Працівник депо; водій
- Trigger: Нестача місткості на маршруті
- Preconditions: У D1 є місткість, резерв і доступність водіїв
- Main flow:
  1) Диспетчер обирає маршрут і часовий горизонт.
  2) C3 готує агрегований попит і поточне завантаження.
  3) C4 у повній системі оцінює попит; для прототипу це ручний вхід.
  4) C5 порівнює варіанти резерв/зміна інтервалу/без змін [DP-03].
  5) Диспетчер і депо підтверджують ресурс та випуск.
  6) C6 передає погодження; C7 фіксує рішення й наслідок.
- Alternative / exception flows: A1: резерв відсутній → обрати іншу дію. E1: прогноз попиту відсутній → рішення людини за фактичними лічильниками.
- Output / outcome: План додаткового рейсу з автором погодження.
- Constraints (NFR): Доступ за ролями; підтвердження ресурсу перед випуском.

### UC-04: Обробити дефектну телеметрію
- Primary actor: Оператор інтеграцій
- Secondary actors: Бортовий пристрій; адміністратор
- Trigger: Надходження нової події
- Preconditions: Відома схема record_id, trip_id та UTC timestamp
- Main flow:
  1) C2 перевіряє обов’язкові поля й допустимі діапазони.
  2) C2 перевіряє повтор record_id [DP-06].
  3) C2 оцінює свіжість та необхідні ознаки [DP-05].
  4) Коректні події потрапляють у D1, дефектні — у карантин.
  5) Оператор отримує агрегований сигнал при серії дефектів.
  6) C7 записує причину відхилення та версію схеми.
- Alternative / exception flows: A1: повтор події → ідемпотентно ігнорувати. E1: немає маршруту → карантин та перевірка довідника.
- Output / outcome: Перевірена подія або запис карантину з причиною.
- Constraints (NFR): Не передавати платіжні реквізити у C4; не підміняти відсутній GPS нулем.

### UC-05: Опублікувати зміну маршруту
- Primary actor: Диспетчер
- Secondary actors: Служба руху; водій; пасажири
- Trigger: Повідомлення про перекриття
- Preconditions: Диспетчер має право погоджувати зміни
- Main flow:
  1) C1 приймає джерело повідомлення і ділянку.
  2) Диспетчер перевіряє достовірність та обирає варіант об’їзду [DP-07].
  3) C5 перевіряє зупинки, часові межі та повноваження.
  4) Людина погоджує зміну, C3 формує нові прив’язки рейсів.
  5) C6 надсилає повідомлення пасажирам і водіям.
  6) C7 фіксує версію маршруту та доставку.
- Alternative / exception flows: A1: інформація не підтверджена → лише внутрішнє попередження. E1: об’їзд невідомий моделі → розклад/ручне ETA замість ML.
- Output / outcome: Версійована зміна маршруту з повідомленнями.
- Constraints (NFR): Зміна маршруту завжди погоджується людиною; відкат доступний.

### UC-06: Перевірити якість прогнозів
- Primary actor: Аналітик
- Secondary actors: Диспетчер; відповідальний за модель
- Trigger: Планова перевірка або сигнал C7
- Preconditions: Зібрано прогноз та фактичний час прибуття
- Main flow:
  1) Аналітик обирає період і маршрути.
  2) C7 зіставляє прогнози з фактами без майбутніх ознак.
  3) Розраховуються MAE, RMSE та покриття інтервалу.
  4) C7 перевіряє пороги деградації [DP-08].
  5) Аналітик обирає залишити/дослідити/вимкнути версію.
  6) Рішення і зріз метрик записуються до D3.
- Alternative / exception flows: A1: бракує фактів → статус insufficient evidence. E1: змінився маршрут → окремий зріз, заборона узагальнювати старі метрики.
- Output / outcome: Звіт якості та рішення щодо версії.
- Constraints (NFR): Метрики окремо за маршрутом/часом; персональні ідентифікатори не потрібні.

### UC-07: Допустити нову версію моделі
- Primary actor: Відповідальний за модель
- Secondary actors: Аналітик; адміністратор
- Trigger: Завершення навчання кандидата
- Preconditions: Є схема ознак, контрольний набір та попередня версія
- Main flow:
  1) C7 реєструє кандидата в D2.
  2) Аналітик перевіряє відкладені дані й stress cases.
  3) Відповідальний оцінює метрики, сумісність та ризик [DP-09].
  4) Людина погоджує допуск або повертає на доопрацювання.
  5) C4 завантажує погоджену версію зі збереженням попередньої.
  6) C7 контролює canary-вікно і можливість відкату.
- Alternative / exception flows: A1: метрики не гірші, але покриття слабке → додаткова перевірка. E1: несумісна схема → заблокувати допуск.
- Output / outcome: Версія моделі з протоколом допуску або відмовою.
- Constraints (NFR): Без автоматичного самонавчання на неперевірених діях диспетчера.

### UC-08: Розібрати скаргу на прогноз
- Primary actor: Диспетчер
- Secondary actors: Пасажир; аналітик
- Trigger: Скарга про хибне ETA
- Preconditions: Відомі зупинка та приблизний час події
- Main flow:
  1) C1 приймає мінімальні дані скарги.
  2) C7 знаходить прогноз, модель і вхідний зріз.
  3) Людина зіставляє факт та прогноз і класифікує причину [DP-11].
  4) Аналітик вирішує, чи придатний випадок для навчання [DP-12].
  5) C1 повертає пасажиру відповідь без службових персональних даних.
  6) C7 зберігає перевірену мітку та зв’язок з інцидентом.
- Alternative / exception flows: A1: фактичного часу немає → скарга не стає навчальною міткою. E1: дубль скарги → приєднати до існуючого інциденту.
- Output / outcome: Картка інциденту та перевірена/відхилена мітка.
- Constraints (NFR): Мінімізація персональних даних, доступ до журналу за ролями.

## D. Flow mapping (1–2)
### Flow for UC-01
1) C1: пасажир обирає зупинку → C5 запитує C3.
2) C2/C3: перевірка даних [DP-06: дублікат?] → [DP-05: свіжий і повний зріз?].
3) Відхилений зріз → C5: позначений розклад → C1; C7 пише причину.
4) Прийнятий зріз → C4: ETA та q90 → C5 [DP-01: live / попередження / fallback].
5) C1: пасажир отримує картку; C7 зберігає прогноз і версію.
### Flow for UC-02
1) C2 → C3: два послідовних зрізи headway.
2) C5 [DP-04: <50% планового?] → тривога у C1 або спостереження.
3) Диспетчер [DP-02: hold / reject / інша дія] з урахуванням правил.
4) Погоджено → C6 → водій → квитанція [DP-10].
5) Немає квитанції → резервний зв’язок; є → C7/D3: рішення та фактичний наслідок.

### Ризики та перевірка
Хибний ETA при непередбаченому перекритті: вузький інтервал не гарантує правильності; потрібні incident feed, скарги та fallback. Небезпечна рекомендація затримки: C5 перевіряє ліміти, а диспетчер завжди підтверджує дію.
У прототипі ПР6–7 реалізовано UC-01, DP-01 та частину DP-05; решта сценаріїв є специфікацією повної системи.
