## Problem
Нестабільні інтервали руху та неточний розклад створюють невизначеність для пасажирів і ускладнюють роботу диспетчера.

## Users
Пасажири, диспетчери, водії, працівники депо й аналітики. Прототип реалізує інформаційний сценарій пасажира (UC-01).

## Solution
Перевірений часовий зріз телеметрії перетворюється на прогноз часу прибуття. Правила обирають `auto_information`, `review` або `reject`. ШІ не надсилає команди водіям: затримку, випуск і зміну маршруту погоджує людина.

## Architecture
[Фінальна схема](docs/architecture.svg) · [HTML-схема](docs/architecture.html) · [Use cases, decisions та HITL](docs/use_cases_and_decisions.md).

C1 інтерфейси → C5 правила → C3 дані/ознаки → C4 ETA → C5 → C1/C6 результат. Зовнішні джерела → C2 валідація → D1/C3; D2 містить модель, C7 зберігає аудит у D3. У прототипі сховища - CSV/JSON/JSONL.

DP-01: режим публікації ETA; DP-02: підтвердження затримки диспетчером; DP-03: підтвердження резервного випуску. Їхні значення збережено з ПР4. DP-05: перевірка зрізу перед прогнозом. Інші UC/DP описують повну систему й не видаються за реалізовані функції.

## AI component
Числова регресія ETA у хвилинах. Ridge baseline з λ=0.01, вільний член не штрафується. Ознаки: bias, distance/max(speed,5)×60, base×traffic, occupancy, rain та peak. Коефіцієнти навчаються; 90%-квантиль абсолютних залишків оцінюється на окремій calibration-вибірці. Це глобальний інтервал для заданого процесу, а не ймовірність правильності окремої відповіді.

## Prototype
Потрібен Python 3.9+; зовнішніх залежностей немає.

```sh
python3 src/transit.py
python3 src/app.py
```

Відкрити http://127.0.0.1:18765/. Сервер доступний лише на цьому комп’ютері. Для зупинки - Ctrl+C. Якщо порт зайнятий, змінити його у `src/app.py`.

Notebook: `notebooks/CityTransit_ETA.ipynb` (із виконаним виводом). Запускати з кореня проєкту або каталогу notebooks/. Код notebook самодостатній. Повторне виконання детерміновано відтворює дані та результати.

`src/transit.py` створює train/calibration/test CSV, model.json, metrics.json, scenarios.json та checks.json. `src/app.py` показує інтерфейс, викликає модель і записує локальні події до results/audit.jsonl. Це навчальний журнал без production-гарантій незмінності.

## Results
Синтетичні дані: 1200 train (seed 301), 200 calibration (302), 200 test (303). Окремі ID та seed; test не використовується у fit або калібруванні. Ціль згенерована з відомої функції з шумом σ=0.65 хв; фактичні міські поїздки не використовуються.

| Показник на 200 test | Значення |
|---|---:|
| MAE моделі | 0.498 хв |
| RMSE моделі | 0.612 хв |
| MAE distance/speed baseline | 2.672 хв |
| Покриття інтервалу | 94.5% |
| q90 на calibration | 1.155 хв |

Додатково 15 ручних сценаріїв: 10 числових прогнозів, 5 відмов. У 9/10 числових сценаріїв помилка ≤2 хв; очікувані режими 15/15. Сім перевірок охоплюють відокремлення ID, відсутню ознаку, NaN, межі 60/61 с і відсутність команд транспорту.

## Limitations
- Синтетичний генератор та модель мають близьку функціональну форму, тому метрики сприятливі й не підтверджують точності у реальному місті.
- Невідоме перекриття: прогноз 6.73 хв проти заданого факту 22 хв (помилка 15.27 хв), хоча інтервал вузький. Невідомі зовнішні події не виявляються автоматично.
- Вік >60 с, пропуски, NaN, speed поза 5–60, distance поза .2–6 або невідомий weather → reject. Traffic=5, occupancy≥.95 або q90>2 → review. Пороги експериментальні, потребують узгодження.
- Фактичний розклад не підключено: fallback повертає `schedule_labelled`, а не вигадане числове ETA.
- C4 реалізує тільки ETA. Прогноз попиту, dispatch, GPS-потоки, авторизація, реальна доставка та production-сховища залишаються проєктними.
